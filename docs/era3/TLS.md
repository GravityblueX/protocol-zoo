# TLS：在不可信传输上建立条件信任

## 历史问题

HTTP、邮件和其他应用最初可以交换数据，却没有统一的机密性、完整性和端点身份机制。TLS 把协商、密钥交换、认证和记录保护放在应用与传输之间，使应用协议可以复用一套密码学通道；它不证明应用语义正确，也不自动使端点可信。

## 规范与演化

- TLS 1.0/1.1（历史上的 RFC 2246/4346）已不应作为新部署基线。
- TLS 1.2：RFC 5246，仍广泛存在，但具体密码套件和配置决定实际安全性。
- TLS 1.3：RFC 8446，减少握手往返并删除多种旧密码学选项；0-RTT 以重放风险换取特定场景的早期数据，不能无条件用于有副作用请求。
- 记录层与握手层的安全性质由规范共同定义；证书验证、名称匹配、信任锚和密钥生命周期是部署的一部分，而非“加上 TLS”即可完成。

“加密”不等于“匿名”，证书有效也不等于服务内容无恶意。中间盒可能终止并重新建立 TLS；此时两段连接的信任边界不同，不能把端到端机密性描述得过强。

## 仍然存活的部分

TLS 的通用性、可升级性和与现有 TCP 应用的组合方式使其成为 HTTP 等协议的主流安全承载。现代部署通常优先 TLS 1.3，并保留经审计的 TLS 1.2 互操作配置；旧版本、弱密码套件、忽略证书错误和静态密钥复用都属于明确风险。

## 实验边界

本节为 **L0 citation + document reconstruction**，没有把本机浏览器或任意公网握手当作 TLS 版本普遍性的证据。安全复现应在 loopback/netns 使用自签名测试 CA 或合成证书，明确记录客户端验证模式；不得提交私钥、真实证书链、session ticket、cookie 或公网目标数据。若使用 VPS，只能观察自有端点，并按 `VPS-SAFETY.md` 的限制记录时间、路径和软件版本。
